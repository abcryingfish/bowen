# 风格组合增量监控设计

## 摘要

在 `可视化/模型有效性/index.html` 中，将当前演示曲线改为真实的风格组合监控。组合每天按行情和因子增量更新，记录持仓、现金、资产、收益、交易和换手。该功能复用现有风格评分和回测口径，但使用独立的增量账本，不把现有全量回测 runner 改造成日记账。

第一版包含 10 个组合版本：大市值、小市值、价值原始版、价值行业中性版、成长原始版、成长行业中性版、动量、低波、红利和流动性。大小盘是一个风格组的两个方向；多板块成长/价值不纳入。

## 模型与组合规则

### 股票池

- 仅使用 `.SH`、`.SZ` 股票，排除 `.BJ` 和板块指数代码。
- 股票至少有 120 个历史交易日。
- 最近 20 个交易日平均成交额不低于 2,000 万元。
- 当日收盘价、成交量和对应风格分数必须有效。
- 暂不使用历史 ST 状态过滤，因为当前仓库没有可靠的历史 ST 时间序列；避免用当前名称回看历史造成前视。

### 选股与权重

- 每个风格按当日分数截面排序，选前 20%，最多 200 只。
- 高分组合买入前 20%，低分组合买入后 20%；低分组合作为理论“空头腿”，实际仍是独立的多头组合。
- 组合内部等权，按 100 股整数手成交。
- 每个模型同时生成高分多头净值、低分多头净值和高分/低分净值相对曲线，三条线以 100 为共同起点。

### 风格版本

| 模型版本 | 因子来源 | 调仓周期 |
|---|---|---|
| 大市值原始版 / 小市值原始版 | 纯市值风格评分 | 每周 |
| 价值原始版 | 价值模型综合评分 | 每月 |
| 价值行业中性版 | 价值模型综合评分(行业标准化) | 每月 |
| 成长原始版 | 成长风格综合评分 | 每月 |
| 成长行业中性版 | 成长风格综合评分(行业标准化) | 每月 |
| 动量原始版 | 动量风格评分 | 每周 |
| 低波原始版 | 低波风格评分 | 每月 |
| 红利原始版 | 红利基础百分位/评分 | 每季度 |
| 流动性原始版 | 流动性综合评分 | 每周 |

行业中性版本不是新的经济因子，而是现有风格分数经过 881 行业内横截面标准化后的组合版本。当前代码中已经存在的行业中性综合分只有成长和价值，因此不额外为其他风格研发中性分。

### 成交与资金口径

- 初始资金沿用现有回测默认值 `10,000,000` 元。
- 手续费沿用现有 `0.03%` 配置。
- 使用 T 日收盘信号、T 日收盘理论成交；页面必须标注“理论监控”，不能解释为可实盘成交收益。
- 第一版不模拟融券、滑点和涨跌停锁死；高/低分相对曲线只作为风格强弱指标。
- 首次初始化从 `2015-01-01` 回填；行业中性版本从其真实可用日期开始，不与原始版本拼接。

## 增量账本与接口

使用独立 DuckDB 文件 `D:\database\style_portfolio_monitor\style_monitor.duckdb`，不改写 `D:\database\signal_daily` 因子源。核心表/逻辑如下：

- `model_definition`：模型版本、因子键、方向、调仓周期、选股宽度、版本号和配置哈希。
- `nav_daily`：模型、日期、现金、持仓市值、总资产、日收益、累计收益、换手、费用、调仓状态。
- `position_daily`：模型、日期、代码、分数、排名、目标权重、股数、价格、持仓市值。
- `trade_log`：模型、日期、代码、买卖方向、股数、价格、成交额和手续费。
- `run_state`：每个模型最后成功日期、最后调仓日期和配置哈希。
- `update_run`：更新任务状态、处理区间、进度、失败日期和错误信息。

手动更新从每个模型最后成功日期补到该模型所需数据的共同最新交易日。每天按事务处理；当日失败回滚且不推进水位。同一天重复更新必须幂等，不重复交易或写入净值。调仓日因子有效覆盖率低于 80% 时暂停该模型；非调仓日只做收盘估值。持仓缺收盘价时使用最近有效价格估值并标记数据滞后，新入选股票没有有效价格时不买入。

建议接口：

- `GET /api/style-monitor/summary`：当前日期、各模型最新日期、强弱排名和关键指标。
- `GET /api/style-monitor/curves`：按模型和日期范围返回三类曲线。
- `GET /api/style-monitor/positions`：返回指定模型指定日期的持仓和分数。
- `GET /api/style-monitor/trades`：返回调仓交易记录。
- `POST /api/style-monitor/update`：手动启动增量更新任务。
- `GET /api/style-monitor/update/jobs/{id}`：查询更新进度和失败信息。

## 页面设计

页面不再写死 6 张演示图，而是读取模型定义动态生成 10 张模型图。布局分两层：

1. 顶部风格总览：显示最近 1、5、20 个交易日的相对收益排名、模型最新日期、最近调仓日、持仓数和更新状态。
2. 风格图表区：每个模型版本一张图，同时显示高分多头、低分多头和相对曲线。默认时间范围为最近 60 个交易日，支持 20D、60D、YTD、全部切换和曲线显隐。

点击模型图进入明细，展示当前持仓、股票分数/排名、目标与实际权重、最近交易和换手。页面只提供手动更新按钮，打开页面只读账本，不自动写盘。模型下拉框暂不扩展；后续再把模型定义映射到 `center-backtest-model-option`。

## 异常、版本与兼容

- 原始因子、行情或行业快照缺失时，不用 0 填充；按模型暂停或沿用持仓并记录原因。
- 配置、因子版本或组合口径变化时生成新的 `model_version`，不重写旧账本。
- 页面显示各模型自己的最新日期，不能假设所有模型同步到同一天。
- 所有 JSON、DuckDB 文本字段和前端文件统一 UTF-8。
- 更新任务使用进程锁，禁止两个增量任务同时修改同一账本。

## 验证计划

- 单元测试：排名、前 20% 且最多 200 只、等权目标股数、周/月/季度调仓日、相对曲线公式、缺失数据和 80% 覆盖率门槛。
- 账本测试：首次初始化、断点续跑、重复运行幂等、单日失败回滚、配置哈希变化建新版本。
- 真实数据冒烟：对 10 个模型各跑一个交易日，核对净值、现金、持仓、交易和相对曲线。
- API 测试：summary、curves、positions、trades、update job 的状态和错误响应。
- 页面验证：模型数量动态渲染、曲线时间切换、更新进度、移动端布局和 UTF-8 中文显示。
- 性能验证：重复手动更新不得重复写盘；单日增量不应重新计算整个历史区间。
- 检查 `codex/logs_2.sqlite`（若存在）是否有 TRACE 高频写入及 `logs` insert trigger，不能因本功能新增高频 TRACE 写盘。
