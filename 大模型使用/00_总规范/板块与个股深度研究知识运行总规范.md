# 板块与个股深度研究知识运行总规范

> 作用：新建 Codex 窗口后，只要完整读取本文件及其明确引用的文件，即可继续执行模型主导的单对象深度研究。
>
> 字符编码：所有 Markdown、JSON、JSONL 和 CSV 必须使用 UTF-8；Parquet 字符串按 UTF-8 语义处理。

## 1. 总体目标

研究系统采用“逐一对象、独立研究、增量积累”的方式：

1. 一个 Codex 任务只研究一个板块或一只个股。
2. 大语言模型负责理解对象、提出问题、逐轮联网检索、阅读原文、判断证据、形成主张、评分和预测。
3. Python 只负责读取确定性数据、执行模型指定下载、客观计算、去重、存储、契约校验和发布审计。
4. 板块档案与个股档案分开保存；全局来源知识库共享；知识图谱独立维护。
5. 旧研究只能提供查询线索和历史状态，不能直接继承旧评分或替代本次检索。
6. 新证据与旧结论冲突时必须保留冲突，重新评估，不得为了连贯性忽略新事实。

## 4. 统一标识规范

### 4.1 对象标识

```text
板块实体：SECTOR:{sector_code}
个股实体：STOCK:{stock_code}
机构实体：ORG:{标准化名称或注册代码}
政策实体：POLICY:{发布机关}:{发布日期}:{内容哈希短码}
产业指标：INDICATOR:{指标名称}:{口径}
```

### 4.2 来源与证据

- `source_id` 标识一个稳定来源或数据入口，例如农业农村部政策库、东方财富研报详情入口。
- `evidence_id` 标识一次具体发布内容，不同文章、公告或数据期次必须使用不同 ID。
- `source_version` 标识同一入口下的不同内容版本。
- `content_hash` 用于判断网页或报告是否真的发生变化。
- 同一证据可以支持多个板块或个股主张，但不得复制成多个互不关联的来源记录。

### 4.3 主张与关系

- 一个 `claim_id` 只表达一个可证伪判断。
- 一个 `relation_id` 只表达一个图谱关系。
- 主张必须关联支持证据、反对证据或可复算客观指标。
- 无法确认、检索失败和不适用必须使用不同状态，不得混写为“没有数据”。

## 5. 单对象研究流程

### 5.1 固定步骤

```text
选择一个对象
→ 锁定分析日期和行情边界
→ 读取旧档案和来源经验
→ 理解对象定义、业务边界和同义词
→ 板块读取成分结构；个股读取业务与公司结构
→ 模型自主提出研究问题
→ 六类来源逐轮联网搜索并阅读正文或有效摘要
→ 根据新发现调整下一轮查询词
→ 记录接受、拒绝、冲突和失败原因
→ 进行反向检索和风险检索
→ Python计算行情、财务、估值、资金等客观数据
→ 模型形成原子主张、评分和短中长预测
→ 独立研究任务只写隔离staging、原始证据和共享状态更新候选
→ 主任务执行二次硬审计
→ 主任务串行原子发布正式Parquet/JSON/Markdown和current
→ 主任务串行更新对象档案、全局来源库、失败库和图谱候选
```

### 5.2 板块必答问题

- 板块定义、产业链边界和同义行业口径是什么？
- 成分股中核心业务、上下游、弱关联成分分别有多少？
- 龙头贡献是否掩盖中小成分的恶化？
- 盈利覆盖、收入/利润分布、正利润、亏损和业务纯度如何？
- 政策、产业景气、资金和技术是否相互验证？
- 该板块适用哪一种 `analysis_archetype`？

### 5.3 个股必答问题

- 公司收入、利润和现金流由哪些业务和地区贡献？
- 公司是行业价格接受者、定价者还是周期暴露者？
- 公告中的经营变化是否得到财务、产业和渠道证据验证？
- 估值应与什么公司、什么历史阶段比较？
- 股东、融资、解禁、质押、诉讼、监管和治理风险如何？
- 所属板块观点对该股是否真的适用，业务纯度是多少？

## 6. 六类来源与状态

每次研究必须分别处理：

1. 政策
2. 正式研报
3. 公告
4. 新闻与报道
5. 产业数据
6. 资金数据

证据状态固定为：

```text
valid
no_valid_evidence_after_search
retrieval_failed
not_applicable
conflicted
mismatch
post_date_excluded
```

禁止用主题新闻替代政策原文，禁止用行情稿替代订单或经营证据，禁止把成交方向推算的“主力资金”当作官方资金流数据。

## 7. 来源知识库更新规则

每完成一个对象，必须检查是否发现新的有效来源或失败路径。来源归档属于正式发布的硬门槛，不是可选的善后工作。

### 7.1 有效来源必须记录

- `source_id`
- 来源名称、域名和稳定入口
- 来源类型
- 可覆盖的板块或个股类型
- 可支持的判断维度
- 原文/摘要可用性
- 日期字段可信度
- 访问方式和已知限制
- 最近成功日期
- 最近检查日期
- 生命周期状态和使用优先级
- 来源质量评分：权威性、日期可靠性、内容完整性、对象匹配度、可复现性
- 成功次数、失败次数和最近失败原因
- 成功样例 `evidence_id`

### 7.2 失败路径必须记录

- 失败URL或入口
- 失败类型：证书、反爬、登录、空数据、只有标题、日期不明、内容重复、口径错配等
- 首次和最近失败日期
- 是否可重试
- 替代来源或替代查询方式
- 不应再次重复的错误尝试

失败记录的目的不是永久封禁来源。后续任务可以在来源状态发生变化时重新尝试，但必须说明为什么值得重试。

来源质量评分固定为0到1：

```text
authority_score
date_reliability_score
content_completeness_score
object_match_score
reproducibility_score
```

质量评分不替代证据状态；一个来源可以`valid`但只适合低权重背景说明。

### 7.3 来源生命周期

每个来源必须使用以下状态之一：

```text
active              当前可用，可在适用对象中优先检查
conditional         仅在特定对象、日期、登录状态或内容类型下可用
temporarily_failed  暂时访问失败，满足重试条件后允许复验
deprecated          已被更稳定或更权威的来源替代
invalid             已确认不可靠、口径错误或无法追溯
```

来源状态按新运行增量更新，不删除历史状态。一次访问失败通常只能将来源改为 `temporarily_failed`，不能直接改为 `invalid`。

### 7.4 每次研究结束的强制来源归档

独立研究任务必须在staging中生成以下来源归档候选；主任务在正式发布前审计、合并并串行写入：

1. 汇总本次实际访问的所有来源入口，而不只是最终入选证据。
2. 为新来源生成全局来源注册候选和稳定 `source_id` 候选。
3. 为已有来源生成 `last_checked_at`、成功/失败次数和最近访问结果更新候选。
4. 生成来源适用对象、来源类型、支持维度和已知限制更新候选。
5. 访问失败时生成失败路径候选，并关联原 `source_id` 和替代入口。
6. 发现更权威来源时生成来源优先级调整候选；旧来源保留并建议标记 `deprecated`，不物理删除。
7. 对目标对象有特殊价值的来源，生成对象目录 `有效来源.md` 更新候选。
8. 本次没有产生任何来源变化时，也必须记录 `no_source_registry_change` 和检查时间。
9. 生成来源归档摘要：新增数、复验数、状态变化数、失败新增数、被替代数。

来源归档只能沉淀有参考意义的信息。一次性搜索结果页、无正文标题、重复转载和明显错配内容不进入有效来源注册表，但其可复用的失败经验应进入失败路径库。

## 8. 历史知识复用与路径依赖纠偏

### 8.1 可以复用

- 对象同义词、产业链词汇和历史研究问题。
- 已验证的数据入口、公告入口和研报入口。
- 访问限制、失败原因和替代路径。
- 历史证据ID和旧主张，作为本次待验证线索。
- 可复算的Python计算方法和字段契约。

### 8.2 禁止直接复用

- 旧综合分和六维分数。
- 已过有效期的政策影响、资金状态或技术状态。
- 旧预测和旧结论。
- 未重新核验的搜索摘要。
- 其他板块或个股的通用句式结论。

### 8.3 强制纠偏

- 至少执行一轮反向观点搜索和一轮风险搜索。
- 主动寻找能够推翻核心多头或空头主张的证据。
- 发现冲突时保留双方证据，并降低置信度。
- 连续两轮搜索不再产生新有效主张后才允许停止。
- 旧来源路径只是优先入口，不是唯一入口；每次必须探索最新政策、公告、研报和新数据源。

## 9. 评分与预测

六维顶层定义保持：政策、基本面、资金、技术、估值、风险。

- 风险分是风险压力，越高越危险。
- 风险分不得直接当成正向贡献。
- 证据不足不得自动填5分。
- 板块由唯一 `analysis_archetype` 决定子指标适用性和比较组。
- 个股后续应建立独立适配器，不得直接复制板块子指标权重。
- 预测必须至少包含5、20、60交易日方向、收益区间、上涨概率、置信度和失效条件。

## 10. 知识图谱规则

知识图谱只保存带证据的实体和关系，不把模型推测直接写成事实。

每条关系至少包含：

```text
relation_id
subject_entity_id
predicate
object_entity_id | object_value
relation_status: confirmed | inferred | disputed | expired
confidence
valid_from
valid_to
evidence_ids
analysis_date
run_id
```

关系例子：

```text
政策 → 支持 → 产业方向
产业指标 → 影响 → 板块
板块 → 包含 → 个股
公司 → 供应/采购/竞争 → 公司
公告 → 证明/反驳 → 主张
主张 → 影响 → 评分维度
```

旧关系不物理删除；发生变化时新增版本并将旧关系标记为 `expired` 或 `disputed`。

## 11. 北交所与范围约束

- 当前板块和个股研究默认强制排除北交所股票。
- `.BJ`、`4*`、`8*`、`92*` 等北交所标识不得进入有效成分聚合和评分。
- 北交所来源若被搜索到，记录为 `mismatch`，不得计入有效证据数量。
- 一个任务不得生成其他板块或个股的正式结论。

## 12. 发布与审计

正式发布前必须验证：

- 分析日期边界和发布时间。
- 证据ID唯一、内容哈希可复算。
- 主张均有证据或客观指标。
- JSON可按UTF-8读取。
- Parquet可读取且字段契约正确。
- 板块和个股范围唯一。
- 北交所排除恒等式成立。
- 评分公式可复算。
- 来源归档步骤已完成，并存在本次 `run_id` 对应的归档摘要。
- 本次实际访问的来源均已被登记为新来源、已有来源复验或明确拒绝。
- 来源生命周期状态、最近检查时间和适用范围已更新。
- `staging` 未通过不得进入正式分区。

板块清单和成分快照必须全局原子发布；单对象研究结果按 `run_id` 增量发布。研究失败进入重试；`review_required` 不属于程序失败，不自动重试。

## 13. 对象档案更新

每次研究完成后：

1. 在对象目录的 `历史研究索引.md` 追加 `analysis_date`、`run_id`、报告路径、主要变化和未确认事项。
2. 在 `有效来源.md` 追加本对象验证有效的来源和适用范围。
3. 在 `失败尝试.md` 追加对象特有失败路径和替代方案。
4. 只将跨对象可复用的来源经验同步到全局来源知识库。
5. 将已确认或有价值的争议关系追加到知识图谱候选，不直接覆盖旧关系。
6. 在运行记录中登记来源归档摘要，并将 `source_archive_completed` 设为 `true`。

如果来源归档没有完成，研究内容可以保留在 `staging`，但不得更新正式 `current` 指针，也不得将任务状态标记为 `published`。

## 15. 事实、观点和推断

每条主张和图谱关系必须标记：

```text
fact_type: objective_fact | analyst_claim | market_expectation | model_inference
```

- `objective_fact`：有直接数据、公告或政策原文支持。
- `analyst_claim`：券商、公司或媒体的明确观点。
- `market_expectation`：市场预期或一致预期。
- `model_inference`：模型基于多个证据推导的判断。

只有带有证据关联的`objective_fact`或明确标注来源的观点，才能进入知识图谱；模型推断不得展示为已确认事实。

## 16. 冲突解决

冲突主张必须保留，不得以平均值消除冲突。默认优先级：

```text
官方原文 > 交易所/公司公告 > 正式研报正文 > 权威媒体报道 > 二手转载 > 搜索摘要
```

同层级无法解决时：

1. 记录双方证据和发布日期。
2. 标记`conflicted`或`disputed`。
3. 降低相关评分维度置信度。
4. 写出下一次需要验证的具体问题。

## 17. 对象状态快照

板块和个股历史结果必须引用当时的状态版本：

```text
definition_version
constituent_snapshot_id
analysis_archetype_version
business_profile_version
```

成分、业务边界或类型变化只影响新的分析日期，历史结果不回溯重算。

## 18. 研究资源预算

每个对象在启动时设定预算：

```yaml
max_search_rounds:
max_valid_evidence:
min_evidence_by_source_type:
stop_after_no_new_claim_rounds: 2
min_market_data_coverage:
max_retry_count:
```

预算用于控制上下文和联网消耗，不得为了达到数量强行加入重复证据。连续两轮无新有效主张仍是停止条件。
